# KataGo 训练与课程续训

## Apple Silicon 混合棋盘训练

`train_rl.py mixed` 在同一个官方 `b10c128` 网络中训练 7、8、9、13、19 路。
所有新数据统一使用 19×19 张量和真实棋盘掩码；不会把旧的单尺寸 NPZ 直接拼接进来。
7、8 路支持限于此 KataGo 混训入口，普通版 `train.py` 的棋盘范围保持原样。

本机配置是 [`config/katago_mixed.m4.json`](../config/katago_mixed.m4.json)：

| 项目 | M4 / 16 GiB 初始设置 |
|---|---|
| 搜索推理 / 网络训练 | Metal GPU / PyTorch MPS |
| 网络与精度 | `b10c128`，FP32，不编译，不启用 CPU 算子回退 |
| 棋盘开局抽样权重 | 7:8:9:13:19 = 2:2:3:2:1 |
| 每轮自我对弈 | 24 局，2 个棋局线程，推理 batch 4 |
| 每手搜索 | 50% 使用 32 visits，50% 使用快速 8 visits |
| 训练批次 / 目标更新量 | batch 8，每轮目标 128 批；数据不足时降低批次或先累计回放 |
| MPS 训练内存限额 | PyTorch 建议工作集的 60%，非整机物理内存的 60% |
| 回放 / 保留模型 | 最近约 50,000 行，最近 8 个模型，最近 2 份洗牌数据 |
| 当前默认输出目录 | `training_runs/katago_existing_model_gated_20261030/run` |

权重控制开局棋盘抽样概率，不保证训练行占比。实际局数和回放行数按棋盘分别保存在
`board_statistics.json`。所有尺寸暂时共用中国面积规则、位置全局同形、贴 6.5 目。
这组搜索和批次设置是本机可运行的起点，没有经过长期棋力对比。

先准备与引擎匹配的官方源码到 `katago/source`，安装原生 macOS 依赖和 Metal 引擎：

```sh
brew install katago
.venv/bin/python -m pip install -r requirements-rl-macos.txt
# 本机已验证引擎和官方源码均为 v1.18.2；源码提交 fd0723fdbc0e9d82cf269c9630af8c27c57c07c4。
.venv/bin/python train_rl.py mixed-doctor --hardware mps
```

启动、查看状态和恢复：

```sh
# 默认持续运行；Ctrl+C 会中断子进程并保留已完成的检查点。
.venv/bin/python train_rl.py mixed --hardware mps

# 只运行两轮，或在独立目录做一次短预检。
.venv/bin/python train_rl.py mixed --hardware mps --iterations 2
.venv/bin/python train_rl.py mixed --hardware mps --smoke --games 20 --iterations 1 --run-root training_runs/mixed_preflight

# 查看状态不探测 GPU；重新运行相同启动命令会恢复同一训练目录。
.venv/bin/python train_rl.py mixed-status
```

`--mixed-config` 可指定另一份混训配置。
MPS 混训可用 `mps_game_threads` 指定并行对局数。推理批量和搜索次数由各自配置控制。
`mps_hybrid_inference` 开启时，有网络的常规自对弈使用两条 Metal GPU 和两条 Core ML
（CPU＋神经引擎）推理线程。该选项需要支持混合推理的 KataGo Metal 引擎。

新训练先用 KataGo 官方随机启动器采集数据；
可复现的学习器种子保存在 `initial_model/model.ckpt`，不会提前发布成自博弈网络。
学习器在 MPS 上更新；冷启动期间，每新增约 4,096 样本，候选网在独立目录试下
100 局，通过基本数据质量检查后才接管自博弈。`bootstrap_state.json` 的 `warming`
表示仍在随机供数预热，`ready` 表示已通过冷启动验收，不表示达到某个棋力等级。
探测数据不会进入训练回放，续训恢复网络、优化器和验收状态。
原有旧训练目录不自动改写；明确缺少完整检查点的已训练目录会拒绝从随机种子假恢复。
根因、对照与修复证据见 [冷启动问题定位](research/KATAGO_COLD_START_ROOT_CAUSE_20261030.md)。
10 月 24 日的旧目录保留作对照，不会自动重写。当前默认目录是从完整模型、优化器
恢复并通过候选探测和实际棋谱复核的分支。
`health_by_board.json` 的 `warming_up` 仅表示某尺寸统计窗口还不足64局，
与 `bootstrap_state.json` 的模型准入阶段不同；应分别解读两个状态。
没有混训清单的已有数据目录会被拒绝，棋盘、抽样权重、规则或模型结构与清单不一致时也会停止。
需要更改这些内容时，请使用新的输出目录。

官方训练器按完整数据分片处理，目标更新量不是严格的步数上限，实际计数见检查点和指标。
每轮结束清理旧模型、洗牌数据和回放，保留棋谱、日志和配置历史；后者仍会增长。
可用磁盘低于 10 GiB 时停止训练。导出版本数和对战晋级次数分别记录。

### 对战晋级

混训配置中的 `"promotion": {}` 启用晋级。启用后的首次启动会冻结最新的已训练导出，
在每种棋盘独立试下 32 局，通过健康检查后将其登记为初始冠军，晋级计数从 0 开始。
冷启动预热完成后才会执行这项检查。持续训练期间，只有冻结冠军用于正式自对弈。

正式配置现统一使用 `unified_v1`，完整规则见[统一训练标准](TRAINING_STANDARD.md)。
每累计 51,200 个实际训练样本评测一次候选。每种棋盘初筛 12 局、确认赛 40 局，搜索 32 visits。
初筛和确认赛使用不同开局，每个开局交换黑白各下一局。确认赛要求总得分率至少 55%、
每种棋盘得分率至少 50%；配对得分的单侧 Hoeffding 下界仅供参考。
Mac 默认配置用 `promotion.evaluation_boards` 将晋级对战限定为 8、9、13、19 路，
初筛共 48 局、确认赛共 160 局。`promotion.standard` 设为 `unified_v1`，
总得分率达到 55% 且各受评棋盘至少 50% 即可进入健康验收。统计下界继续记录供参考。
两项配置只影响新晋级挑战，7 路仍参与训练及健康验收。
`promotion.parallel_pairs` 控制同时执行的换色开局组数。Mac 当前设为 2，每组仍完整
下两局黑白互换棋。并发数随挑战记录冻结，重启会沿用该场开始时的设置。
确认赛通过后，候选还须用自身进行逐棋盘健康检查。任一尺寸的黑方得分率超出
10%–90%，或短局、开局双停、无结果、停着率等指标超标时，候选会被拒绝。
极端分差率仅统计和展示，供观察，不阻止初始冠军准入或候选晋级。
初筛、确认赛和健康探测的对局与训练回放隔离。

`mixed-status` 的 `promotion` 字段显示冠军、晋级次数、下次评测样本水位和最近决策。
状态保存在运行目录的 `promotion/state.json`，评测证据保存在 `promotion/evaluations/`。
评测中断后续跑会复用已校验的成对对局。某尺寸至少有 24 局来自现任冠军后，
若实际自对弈出现持续偏色、短局或停着异常，训练会在打乱数据前停止，并保留原因供复查。

2026-10-24 已通过正式入口的五棋盘真实预检：20 局均有效，五种尺寸均有样本，
batch 8 MPS 更新、种子传递和导出成功。完整测试 563 项，其中 560 通过、3 项平台相关跳过。

本次启动的后台进程元数据、PID 和准确停止命令保存在输出目录的 `process.json`，
标准输出保存在 `training.stdout.log`。后台停止应向该 PID 发送 `SIGINT`，
例如 `kill -INT <PID>`，随后等待进程退出；不要同时在同一目录重复启动。

### 分棋盘诊断与独立评测

Mac 混训与 Windows RTX 课程共用「棋迹」实时监控。Mac 在项目目录启动
`.venv/bin/python monitor_training.py --run katago_existing_model_gated_20261030` 后，
可打开 [本机统一监控](http://127.0.0.1:8766/) 查看训练总览、评测晋级和分棋盘诊断。
每 2 秒读取记录；候选对冠军的比分随已结束对局更新，损失与吞吐在每轮训练完成后更新。
各运行目录的 `dashboard.html` 仍可离线打开。

每轮完成后生成 `health_by_board.json`：按棋盘各取最近 256 局，至少 64 局后
标记双 pass、极短局、大目差、无结果或黑白胜负偏向，并附原始棋谱样例和来源模型。
诊断报告提供复查线索。启用晋级时，冠军自对弈另有上述停机检查。
`mixed-status` 返回上次诊断快照；以下命令在 CPU 上立即刷新，允许训练继续运行：

```sh
.venv/bin/python train_rl.py mixed-health
```

评测前先停止同一 GPU 上的训练。显式指定对手和新目录；候选省略时在首次运行
选定最高训练水位模型。模型、引擎二进制、规则、贴目和固定开局均绑定 SHA-256。
每个开局交换黑白各下一局，逐对保存棋谱证据；相同参数重试只复用通过校验的完整对局。

```sh
.venv/bin/python train_rl.py mixed-evaluate --hardware mps \
  --baseline-model /absolute/path/to/baseline.bin.gz \
  --evaluation-output training_runs/mixed_eval_new \
  --evaluation-games 12 --evaluation-visits 32
```

若棋局达到手数上限而没有终局结果，评测会拒绝计分。可以用
`--evaluation-max-moves-factor 6` 将每局新增手数上限提高到面积的六倍，
并使用新的评测目录；该参数绑定冻结协议，不能在原目录中改变。
默认仍为 2.5。2026-10-30 的分析、评测修正和隔离恢复结果见
[问题分析与恢复](research/KATAGO_ANALYSIS_AND_RECOVERY_20261030.md)。

每种棋盘结果分别写入 `summary.json`，保留逐局描述性 Wilson 区间及按开局对
计算的保守区间；同一开局的两局有相关性。少量固定开局只能作试验观察，不能
推出通用棋力、稳定 Elo 或晋级结论。主训练没有自动评测晋级门控。

### 固定时长的开局对照试验

源训练停止后准备新目录。准备阶段只用 CPU，冻结完整网络、优化器、SWA、计数
和保留回放。NPZ 与检查点修改时间保持一致，以正确恢复已清理数据的累计行号。
两个分支共用相同起始状态；处理组以 10% 概率使用独立生成的合法 SGF 局面。
默认局面池为 30 个非空根节点布局（2/4/6 颗棋子），各尺寸数量为 6:6:9:6:3，
原生 SGF 读取后每个文件恰好一个局面，保持配置的棋盘概率。一般浮点权重只能
用有限整数池近似，清单会记录实际概率与误差；布局没有此前的着手历史。

```sh
.venv/bin/python train_rl.py mixed-experiment-prepare \
  --experiment-output training_runs/mixed_trial_new --budget-seconds 180
.venv/bin/python train_rl.py mixed-experiment-run --hardware mps \
  --experiment-output training_runs/mixed_trial_new \
  --evaluation-games 12 --evaluation-visits 32
```

两组串行运行，各有固定的训练墙钟预算；初始模型均提前导出，到时发送 SIGINT，
另行记录退出用时。`trial_result.json` 保存实际完成的训练样本、生成行、保留行、
各尺寸局数和健康度、已完成周期的分阶段秒数，以及对同一冻结 SWA 对手的评测。
计时包含训练进程启动和未完成阶段；阶段秒数之和只包含已完成周期。
官方随机序列独立采样，一轮短试验不能证明因果增益。

执行是一次性的：已开始的试验不会通过重试获得额外训练时间。失败或中断的目录
保留供检查；其中冻结评测可通过相同 `mixed-evaluate` 参数单独恢复。
再次训练请准备新试验目录。完成后用原 `mixed --hardware mps` 命令恢复基线训练。

在同一冻结快照上准备后续资源试验：

```sh
.venv/bin/python train_rl.py mixed-budget-prepare \
  --experiment-output training_runs/mixed_trial_new \
  --destination training_runs/mixed_budget_candidates_new
```

生成控制组，以及每次只改一项的 `search64`（完整搜索 64、快速搜索仍为 8）、
`cycle96`（每轮 96 局）、`replay25000`（回放上限 25,000 行）、`more19`
（尺寸权重 2:2:3:2:2）。完整初始状态和原回放逐份复制到独立目录；回放缩小
发生在执行阶段，准备阶段不删初始数据。清单包含固定时长 API、执行命令和
参数哈希；`cycle96` 显式传 `--games 96`，覆盖 MPS 自动档每轮 24 局的限制。
此命令只准备候选，后续应逐个串行执行并对同一冻结对手评测后再选择配置。
第一轮 SGF 与资源候选均已在本机完成固定时长训练和真实评测，原配置继续保留。
具体数据、区间解释及验收记录见
[2026-10-24 混训对照报告](research/KATAGO_MIXED_PILOT_20261024.md)。
这一轮完整测试为 647 项，644 通过、3 项平台相关跳过。
2026-10-27 续跑检查发现系统重启导致进程停止，同时自博弈存在明显执色偏向；
新增的教师数据隔离试跑已完成真实 MPS 更新，但短更新尚未显示明确棋力收益。
检查过程与限制见 [训练诊断及教师试跑](research/KATAGO_TRAINING_DIAGNOSIS_20261027.md)。

## 多电脑轮流接力

`train_rl.py` 支持导出、校验和导入 KataGo 接力包；训练仍在当前电脑的本地
硬盘和 GPU 上运行。接力包包含完整续训检查点、训练数据、模型、课程状态和
配置，并记录文件 SHA-256 及代码版本。导入只准备新目录，不会自动启动训练。
导出成功后原训练目录会进入接力暂停状态，防止旧计划任务重新接管同一份训练。

先禁用原电脑的自动训练任务并停止训练，再执行：

```powershell
py train_rl.py handoff-export --bundle handoff_bundles\handoff-0001.gogogo-handoff.zip
py train_rl.py handoff-verify --bundle handoff_bundles\handoff-0001.gogogo-handoff.zip
```

把接力包复制到另一台电脑后，导入到尚不存在的新目录，并核对完整检查点：

```powershell
py train_rl.py handoff-import `
  --bundle handoff_bundles\handoff-0001.gogogo-handoff.zip `
  --destination training_runs\relay-0001
py train_rl.py handoff-check --destination training_runs\relay-0001 --load-checkpoint
```

使用导入结果中的 `resume_command` 在新电脑继续训练。第一次跨电脑恢复还应
确认实际训练日志中的累计训练计数延续，并确认成功完成一次更新。检查点读取
验证不会运行 GPU 训练，不能代替该验收。

完整交接步骤、不同显卡配置、单棋盘模式和撤销接力见
[多电脑 KataGo 接力训练](TRAINING_HANDOFF.md)。模型与接力包保持在本地；
这些命令没有 Git 提交、推送或云端上传动作。

## Windows 三档硬件适配

`train_rl.py` 和 `scripts/start_curriculum.ps1` 在启动训练时默认自动检测硬件。
检测会执行一次真实 CUDA 张量运算，选择可用显卡中显存最大的一张；检测失败则
使用 CPU。`status`、`curriculum-status` 等查看状态的命令不需要初始化 GPU。

| 档位 | 自动选择条件 | 自我对弈资源 | 9 / 13 / 19 路训练批次上限 |
|---|---|---|---|
| 无显卡 `cpu` | 没有当前 PyTorch 可用的 CUDA 设备 | 最多 4 个棋局线程、推理批次 1、每轮最多 4 局 | 16 / 8 / 4 |
| 低端显卡 `low` | 可用 CUDA 未达到高端条件 | 32 个棋局线程、推理批次最多 16、每轮最多 32 局 | 显存 ≤4 GiB：64 / 32 / 16；其余：256 / 128 / 64 |
| 高端显卡 `high` | 显存 ≥12 GiB 且计算能力 ≥8.0 | 保留当前配置的并发与对局数 | 1024 / 2048 / 1280 |

这些阈值是保守的资源预设，尚未覆盖所有显卡的实机性能测试。可用 BF16 的显卡
使用 BF16，否则计算能力 ≥7.0 使用 FP16，更早的设备使用 FP32；CPU 使用 FP32。
旧显卡的可用性还取决于安装的 CUDA/PyTorch 版本。AMD、Intel 或无法执行 CUDA
运算的 NVIDIA 显卡目前归入 CPU 档，不启用 OpenCL/DirectML 训练。

三档保留配置内的网络结构、搜索访问量、规则、评测局数和晋级门槛，原来的
`b10c128` 模型可续训。换到较小设备时，会限制课程状态中缓存的训练批次，而不
改写已保存的批次。GPU 阶段迁移按当前精度及显存限制测试候选批次；CPU 使用小
批次，并在发布迁移目录前实际验证一次 CPU 训练。CPU 的完整课程和 200 局评测
会很慢，适合小规模验证；这里没有降低评测预算来改变晋级条件。
小批量对弈会持续累计至原来的最低回放样本数，再进行训练；健康检查按实际局数
向前扩展记录窗口，仍要求默认至少 10 个训练周期、1280 局对局记录。

```powershell
# 只检测硬件，不启动训练
.\.venv\Scripts\python.exe train_rl.py hardware

# 自动选择档位并续训课程
.\.venv\Scripts\python.exe train_rl.py curriculum

# 手动限制资源；不会另起一套模型
.\.venv\Scripts\python.exe train_rl.py curriculum --hardware low
.\.venv\Scripts\python.exe train_rl.py curriculum --hardware cpu

# 完全沿用原配置（兼容此前的启动行为）
.\.venv\Scripts\python.exe train_rl.py curriculum --hardware configured
```

CPU 自我对弈需要单独的 Eigen 引擎，首次安装执行：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\install_katago_cpu.ps1
.\.venv\Scripts\python.exe train_rl.py doctor --hardware cpu
```

安装脚本校验固定发布包的 SHA-256，并将 CPU 引擎放到 `katago/cpu/`。使用官方
v1.18.1 非 AVX2 Eigen 包；[v1.18.2 发布说明](https://github.com/lightvector/KataGo/releases/tag/v1.18.2)

### 定向局面与普通版强制探索实验

`self_play.targeted_start_probability`（默认 0，最大 0.5）和
`self_play.targeted_positions_directory` 用于 KataGo 后端的定向开局。目录包含
`.startposes.txt` JSON 行文件；每条记录保存完整落子历史，使用空 `hintLoc`，
不指定“正确落点”，额外策略初始化为 0，规则和贴目继续遵循当前训练配置。
`weiqi/rl_targeted_positions.py` 从训练棋谱中每盘选一个胜率变化较大的局面，
按整盘棋哈希划分采样与验证集合，不读取正式评测棋谱。胜率变化仅是弱点启发式。

普通版 `search.forced_playouts_coefficient`（默认 0）控制根节点强制探索，
`search.policy_target_pruning`（默认 false）控制训练目标剪枝。两者仅作用于
完整自对弈搜索，评测搜索和廉价搜索不受影响。落子使用实际访问分布，训练单独
保存剪枝后的目标；最佳访问分支保留，搜索访问数及价值回传不修改。
KataGo 官方后端已有自己的强制探索和目标处理，不使用这两个普通版参数。
官方后端的强制探索由 `search.katago_forced_playouts_coefficient` 控制，默认 2，
与本项目一直使用的官方 selfplay 配置一致；0 用于关闭强制探索的消融实验。

2026-10-28 的隔离实验脚本是 `scripts/benchmark_targeted_forced.py` 和
`scripts/benchmark_native_forced.py`，产物位于
`training_runs/targeted-forced-20261028/`。正式训练在完整轮次保存后冻结，实验
不写入正式回放、冠军或评测计数。三个 KataGo 对照分别是原配置、10% 定向开局、
关闭根节点强制探索；每组请求 512 局，搜索访问量 400，256 线程，推理批次 128。
普通版额外分开比较原搜索、仅强制探索、强制探索与目标剪枝；现有普通版检查点
仅完成一轮训练，结果只作为功能和短期策略学习验证，不替代长期棋力评测。


本次实验已完成：正式检查点冻结于 `gogogo-s11814400-d8388521`，三个配置
各生成 512 局，共 1536 局，无损坏棋谱或无结果。实际结果为：

| 配置 | 生成耗时 | 新记录 | 定向开局 |
| --- | ---: | ---: | ---: |
| 原配置（强制系数 2） | 663.56 秒 | 37,009 | 0 |
| 10% 定向采样（系数 2） | 627.69 秒 | 34,762 | 46 |
| 关闭强制探索（系数 0） | 630.27 秒 | 36,522 | 0 |

生成耗时是顺序短测；定向棋局从中盘开始，局数加快不等同于每秒生成更多训练记录。
每组从相同检查点与优化器状态做两次训练，每次 64×1280＝81,920 个梯度样本，
遵守新数据最多复用 4 次的上限。六次训练均推进全部 90 份优化器状态 64 步，
450 个浮点张量有限，90 份模型张量变化。每组首次打乱约 132～133 秒，
每次训练约 36～37 秒；第二次复用不可变打乱数据，避免重复处理成本。

留出新棋局按完整棋局哈希划分，三个共同留出集共保留 12,428 条记录；按完整
批次实际评估 12,032 条。10% 定向采样的策略损失变化在三个集合上为
−0.034%、约 0%、+0.036%，各自的配对棋局 bootstrap 95% 区间均跨零；
价值预测损失增加 0.37%～0.51%，这些短测区间均高于零。关闭强制探索的
策略和价值损失也没有稳定改善。另用成熟 KataGo 对 64 个未参与定向采样的
弱点棋局局面各做 800 访问标注：定向采样策略损失变化 −0.074%
（区间 −0.320%～+0.151%），关闭强制探索 −0.022%
（−0.169%～+0.114%），均不足以证明收益。

普通版完成 96 个固定局面×2 个搜索种子的三组对照，并按原始来源棋局分开
